## Purpose

HazRob 0.6.0 is the first application release built around the compact four-tab HazRob master ESP32 firmware/API v3. It moves analytical, scientific-data, media and experimental intelligence workloads to Android while retaining deterministic actuator/sensor safety functions on the ESP32.

## Operator workflow

Normal USER mode contains:
- Control
- Measurement & Analysis
- History & Reports
- Settings

DEVELOPER mode additionally exposes Experiments & Calibration after the session PIN gate. Developer reference/calibration tools are not present in the normal-user navigation path.

The obsolete standalone v0.5 sensor/chemical/physical tabs were removed from source before the final build; the unified workflow is now the only operational path.

## Key 0.6 capabilities

- `/diag` + `/data` API-v3 normalization with existing drive/STOP/relay/measurement/config endpoints.
- Unified environment/MQ/chemical/physical measurement workflow.
- Dynamic chemical database beyond the legacy 144-entry model.
- Pinned official scientific datasets with CI integrity checks:
  - 652 NIOSH chemical identity/CAS records;
  - 402 NIOSH IDLH records;
  - 638 normalized OSHA Table Z-1 limit records.
- Explicit separation between chemical-knowledge coverage and actual MQ analytical coverage.
- Default/legacy MQ `R0=10` no longer enables quantitative PPM or exposure risk.
- MQ time-series, transient-response features and clean-air sensor health/drift assessment.
- Developer reference captures using dynamic chemical UID/CAS/name selection.
- H.264/MP4 recording of the existing ESP32-CAM MJPEG stream on the phone.
- Experimental temporal flame evidence with event persistence/region metadata.
- Motion breadcrumbs and advisory compound-specific gas-direction estimation.
- Immutable reference JSON export and optional direct publication of APPROVED developer records to the dedicated GitHub `reference-bank` branch using a session-only developer-supplied credential.
- PDF/XLSX field reports and preserved upgrade signing identity.

## Experimental / non-validated claims

The following are implemented as research/prototype capabilities and require controlled physical validation before any stronger claim:
- visual flame recognition accuracy/generalization;
- gas-source direction estimation;
- sensor drift thresholds across long-duration deployment;
- chemical fingerprints/calibration curves generated by future reference-gas experiments;
- any quantitative PPM result not backed by a validated device-specific calibration path.

## Deferred functions

Not part of the 0.6 acceptance baseline:
- 4G/VPN remote transport;
- autonomous return after Wi-Fi loss;
- autonomous gas-plume following;
- thermal camera/sensor fusion;
- physical analog MUX expansion;
- ESP-NOW sensor nodes.

## Physical acceptance required before conference/demo promotion

Use `docs/INTEGRATION_AUDIT_v0.6.md` as the controlling checklist. At minimum validate the physical ESP32 API, STOP/failsafe, relays, six MQ channels, BME/BMP, ESP32-CAM stream/flash, signed upgrade/migration, reports, video recording, developer reference workflow, one scoped GitHub publication test, flame false-positive behavior and controlled gas-direction trajectories.

No product certification or compliance-grade gas-measurement claim is implied by this software release candidate.
